# Сборка и структура проекта

Проект разделён на общее ядро и варианты решателя. Существующая реализация
Gurobi сохранена, включая отдельную программу с генерацией столбцов.
CP-SAT выбирает маршруты из полного результата того же препроцессинга.
Структура целочисленной модели совпадает с Gurobi; в CP-SAT длительности
маршрутов, дополнительной загрузки и лимиты смен округляются вверх до целых
минут (`ceil`) после препроцессинга. Gurobi сохраняет исходные дробные времена.
LP-отбор столбцов пока остаётся только в варианте Gurobi.

В общем препроцессинге исправлено сопоставление продуктов резервуарам:
оно следует числовым индексам выбранных АЗС и учитывает удаление пустых станций.
Строковый порядок ключей JSON (`0, 1, 10, …, 2`) больше не влияет на продукты.
Отсутствующие продукты или неверное число продуктов у выбранной АЗС вызывают ошибку.

```text
apps/gurobi/        main.cpp и col_gen_main.cpp — две точки входа
apps/cpsat/         main.cpp — выбор полного пула через CP-SAT
src/common/        парсер, генерация маршрутов, ДП и расчёт времени
src/gurobi/        модель Gurobi и отбор столбцов через LP
src/cpsat/         модель CP-SAT, проверка решения и отчёт
include/common/    общие заголовки и обработка путей запуска
include/gurobi/    интерфейсы существующего решателя
include/cpsat/     интерфейс модели и результата CP-SAT
third_party/       json.hpp и сохранённые старые заголовки Gurobi
cmake/             отдельные конфигурации gurobi.cmake и cpsat.cmake
scripts/           отдельные команды сборки для Windows и macOS/Linux
data/              входные JSON, копируются вручную и не попадают в Git
outputs/           новые результаты запусков, не попадают в Git
build/gurobi/      сборка Gurobi, не попадает в Git
build/cpsat/       независимая сборка CP-SAT
tests/             проверка модели полным перебором и синтетический JSON
archive/           исторические логи, прежний col_gen.exe и push-test.txt
.codex-context/    локальные инструкции, карта, модель, отчёты и заметки; вне Git
```

Нужны CMake 3.21+ и компилятор C++17. OpenMP подключается, если доступен;
иначе подготовка маршрутов работает последовательно. На Windows рекомендуется
запускать команды из Developer Command Prompt установленной Visual Studio
с компонентами C++. Сборка ориентирована на Release и динамический MSVC runtime
(`/MD`). JSON и лицензии в репозиторий добавлять не нужно.

## Gurobi на компьютере с установленным SDK

В Windows (CMD), подставив путь к своей установке:

```bat
set "GUROBI_HOME=C:\gurobi1203\win64"
set "PATH=%GUROBI_HOME%\bin;%PATH%"
scripts\build_gurobi.bat
```

На macOS/Linux:

```sh
export GUROBI_HOME=/path/to/gurobi/platform
sh scripts/build_gurobi.sh
```

Путь `GUROBI_HOME` должен содержать папки `include` и `lib`. Сборка использует
заголовки и библиотеки установленного SDK; копии в `third_party/gurobi_headers`
сохранены для истории и не входят в include-пути CMake. Для Windows по умолчанию
ищется C++-обёртка `gurobi_c++md2017`; если установлена другая совместимая
обёртка, её можно указать явно:

```bat
scripts\build_gurobi.bat -DGUROBI_CXX_LIBRARY_RELEASE="C:/path/to/wrapper.lib"
```

Лицензия нужна для работы оптимизатора. Её настройка остаётся локальной на
компьютере с Gurobi. Принципы подключения SDK:
[официальная инструкция Gurobi для CMake](https://support.gurobi.com/hc/en-us/articles/360039499751-How-do-I-use-CMake-to-build-Gurobi-C-C-projects).

## Сборка CP-SAT

Нужен C++ SDK OR-Tools 9.15 или новее для своей ОС и архитектуры. Проверенная
версия — 9.15.6755. Скачать и распаковать можно из
[официального релиза OR-Tools](https://github.com/google/or-tools/releases/tag/v9.15).
Python-пакет `ortools` не заменяет этот C++ SDK. `ORTOOLS_ROOT` — корень
распакованной поставки с `include/` и `lib/`.

```bat
set "ORTOOLS_ROOT=C:\deps\or-tools"
set "PATH=%ORTOOLS_ROOT%\bin;%ORTOOLS_ROOT%\lib;%PATH%"
scripts\build_cpsat.bat -DORTOOLS_ROOT="%ORTOOLS_ROOT%"
```

Или на macOS/Linux:

```sh
sh scripts/build_cpsat.sh -DORTOOLS_ROOT=/path/to/or-tools
```

Также поддерживается SDK, распакованный в игнорируемую папку
`build/deps/ortools/`: CMake обнаруживает его автоматически, если явный корень
не задан. Для этой сборки Gurobi и его лицензия не требуются.

Оба скрипта можно заменить прямыми командами из корня проекта:

```sh
cmake --preset gurobi
cmake --build --preset gurobi --parallel
# Или независимый вариант:
cmake --preset cpsat
cmake --build --preset cpsat --parallel
```

Локальные настройки конкретного компьютера можно хранить в игнорируемом
`CMakeUserPresets.json`. Разделение настроек описано в
[документации CMake Presets](https://cmake.org/cmake/help/v3.21/manual/cmake-presets.7.html).

## Данные и запуск

После клонирования создать папку `data/` и положить туда исходные JSON.
Вся папка, включая `.gitkeep`, игнорируется Git. Запускать из корня проекта; тогда без аргументов
используется `data/16_depot.json`. Можно передать другой файл и путь отчёта:

```bat
build\gurobi\bin\Release\truck_routing_gurobi.exe data\16_depot.json outputs\gurobi\main.txt
build\gurobi\bin\Release\truck_routing_gurobi_colgen.exe data\16_depot.json outputs\gurobi\col_gen.txt
build\cpsat\bin\Release\truck_routing_cpsat.exe data\16_depot.json outputs\cpsat\main.txt
```

На macOS/Linux пути используют `/`, имена программ — без `.exe`.
Аргумент `--help` показывает формат запуска. Поддерживается и старый формат
имени JSON без расширения. При отсутствии входа программа завершится с ошибкой;
папки отчёта создаются автоматически. Указанный файл отчёта перезаписывается.

Расчётные параметры сохранены: `R1=3`, `R2=7`, коэффициент времени 1.5,
смена 720 минут, отключённые предварительная загрузка и два шланга,
`load_number=0`, `double_race_number=0`. Они по-прежнему заданы в точках входа,
а не вынесены в новый конфигурационный формат.

Настройки CP-SAT в `CpSatOptions`: 900 секунд, один поисковый поток,
seed 42, нулевые абсолютный и относительный gap. Настройки доступны в C++ API.
Отчёт содержит статус, стоимость, нижнюю границу, выбранные маршруты,
назначения отсеков, исходное и округлённое время. Индексы АЗС в новом отчёте
относятся к отфильтрованному входу, начинаются с 0; старые жёстко заданные
номера конкретного набора данных из отчёта Gurobi не переносятся.

Коды завершения CP-SAT: 0 — найдено допустимое решение, 2 — решение не получено
(статус нужно смотреть в отчёте), 1 — ошибка чтения, построения или проверки.

## Проверка CP-SAT

```sh
ctest --test-dir build/cpsat -C Release --output-on-failure
```

Тесты сравнивают каждое бинарное назначение с независимым описанием ограничений
Gurobi с тем же `ceil`, а затем сравнивают ответ настоящего CP-SAT с полным
перебором. Проверяются дополнительные загрузки/рейсы, пустой `H_k`, покрытие,
веса, округление, индексы и извлечение решения. Искусственный
`tests/fixtures/tiny.json` проходит настоящий препроцессинг; это не рабочие данные.
Для сборки без тестов передать скрипту `-DBUILD_TESTING=OFF`.

Отдельный тест общего ядра проверяет индексы АЗС больше 9, удаление пустых
станций, размеры списков продуктов и генерацию маршрутов с разными видами топлива.
Этот тест доступен в обеих сборках. Для проверки сопоставления на своих JSON:

```sh
build/cpsat/preprocessing_tests data/16_depot.json
```

В многоконфигурационной сборке исполняемый файл находится в `Release/`,
на Windows имеет расширение `.exe`. Эта команда проверяет загрузку и
сопоставление продуктов; рабочие маршруты не генерирует.

25.10.2026: C++-сборка на macOS arm64 с OR-Tools 9.15.6755 и четыре CTest-проверки
прошли, включая 57 моделей и 138457 бинарных наборов. На шести рабочих JSON
проверены загрузка и сопоставление продуктов: несовпадений нет.
Прямое вычислительное сравнение с Gurobi и полная оптимизация рабочих JSON
не выполнялись.

Содержимое `archive/` — прежние результаты, не результаты новых сборок.
Математическая модель и эвристики при разделении папок не менялись.

# Постановка задачи
Алгоритм решает задачу маршрутизации бензовозов с несколькими отсеками на одну рабочую смену (Multi-Compartment Vehicle Routing Problem).

Бензовозы имеют отсеки различной вместимости и могут использовать несколько шлангов для разгрузки топлива. 
Задано множество АЗС, а также время движения между станциями. 
Для подземных резервуаров станций известны виды топлива, а также верхняя и нижняя границы доставляемого топлива. 

Требуется построить маршруты бензовозов для доставки топлива на АЗС, используя минимальное число бензовозов. 
Бензовоз может выполнять несколько рейсов суммарной длительностью меньше длины смены. 
Бензовоз выезжает из депо с полностью загруженными отсеками, каждый отсек бензовоза выгружается целиком в один из резервуаров АЗС, а каждый резервуар заполняется только одним бензовозом.
Разработан алгоритм, позволяющий эффективно получить качественное допустимое решение задачи.

В ходе решения создаётся изначальный набор маршрутов, посещающих не более R1 станций, при этом каждая следующая станция выбирается среди R2 станций, ближайших к предыдущей. 
С помощью алгоритма динамического программирования для каждого маршрута находятся резервуары, которые можно заполнить при выполнении этого маршрута. 
Затем вычисляются длительности маршрутов с учётом возможности ускоренной разгрузки несколькими шлангами. 
Полученные маршруты используются для переформулировки исходной модели в виде задачи о разбиении, которая решается солвером.

## Этапы решения задачи

1. **Генерация допустимых маршрутов**

2. **Поиск всех вариантов заполнения резервуаров для станций в маршруте**

3. **Расчёт времени маршрутов**

4. **Решение задачи о разбиении солвером**

  **Целевая функция (1)**  
Минимизирует число используемых бензовозов.

**Ограничение (2)**  
Отвечает за доступность заправок в соответствии со входными параметрами $a_{ik}$.

**Ограничение (3)**  
Запрещает использовать бензовоз дольше, чем длина рабочей смены.

**Ограничение (4)**  
Отвечает за корректное заполнение резервуаров отсеками: итоговый объем привезённого топлива должен быть больше минимального требуемого объема, но меньше максимальной вместимости резервуара.

**Ограничение (5)**  
Заставляет целиком выливать отсек бензовоза.

**Ограничение (6)**  
Устанавливает связь между числом смен и использованием бензовоза: бензовоз используется, если выходит хоть на одну смену.

**Ограничение (7)**  
Заставляет заполнять все отсеки бензовоза при выходе на смену и не заполнять их в противном случае, а также связывает эту переменную с $y$.

**Ограничение (8)**  
Отвечает за связь $z$ и $y$: привозить груз можно только при посещении этой станции (из некоторой другой станции $j$).

**Ограничение (9)**  
Устанавливает число смен равным числу выездов из депо.

**Ограничение (10)**  
Запрещает останавливаться в промежуточных станциях: если бензовоз приехал в какую-то станцию, он обязан из неё выехать.

**Ограничение (11)**  
Запрещает подциклы: среди $|S|$ станций должно быть не более $|S-1|$ рёбер, чтобы граф был ациклическим. При этом депо не участвует в рассмотрении, так как циклы через депо считаются различными рейсами и допустимы.

**Ограничение (12)**  
Заставляет выгружать первый отсек бензовоза на последней станции рейса.

**Ограничение (13)**  
Позволяет использовать различные шланги только при действительной выгрузке топлива на станции, связывая $t$ и $y$.

**Ограничение (14)**  
Определяет, что каждый отсек выгружается только одним шлангом.

**Ограничение (15)**  
Позволяет выгружать топливо только при посещении станции.

**Ограничение (16)**  
Связывает $h$ и $g$, запрещая посещать станцию бензовозом, не совершающим рейсов.

**Ограничение (17)**  
Отмечает, что первый шланг освобождается не раньше других, гарантируя, что время его работы максимально.
